# 跨包思考指南

本文件不是规范，是判定「一次改动到底影响多大」的思考工具。规划与派发阶段使用。

## 何时必须看另一个包

出现下列任一情况，必须读取对端代码，而不是猜测：

1. 本次改动的字段、状态、错误码会被对端消费。
2. 本次改动的时序（何时可见、何时失效）影响对端的行为。
3. 对端已有针对旧行为的兼容逻辑或特判。

## 契约变更的传播路径

改动一处契约时，按此顺序排查：

1. 定义处（后端 DTO / 表结构 / 前端类型定义 / 公共库导出）。
2. 生产方（构造该结构的代码）。
3. 消费方（读取该结构的代码，前后端均需检查）。
4. 持久化（数据库列、缓存结构、消息体、导出文件）。
5. 兼容层（旧数据、旧客户端、灰度分支）。

任一层未排查，该改动都视为**未完成**。

## 判断改动是局部还是跨层

| 问题 | 局部 | 跨层 |
| --- | --- | --- |
| 改动是否需要同步修改另一包？ | 否 | 是 |
| 是否改变已有数据的解释方式？ | 否 | 是 |
| 是否改变外部可观察的时序？ | 否 | 是 |
| 是否需要在发布窗口上做顺序协调？ | 否 | 是 |

任一为「是」，按标准档任务处理，进入完整复核与派发流程。

## 领域规则的定位

领域规则存放在 `spec/<package>/` 下。规划时：

- 先看本次改动触及哪些规则条目；
- 改动若与现有条目冲突，冲突本身就是 P0，必须在 `prd.md` 中显式处理（改规则或改需求），不得默认让代码服从新需求；
- 若发现规则缺失（本该有条目而没有），在任务结束的 spec 更新阶段补上。
