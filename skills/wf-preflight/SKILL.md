# wf-preflight — 挂机前检查

本技能只服务于一种场景：**你要离开，让 agent 长时间自行执行。**

## 为什么需要它

夜间挂机失败的真实代价不是"跑错了"，而是"跑错后留下一个无法拆解的巨大 diff"。所以挂机前的目标不是"再确认一遍没问题"，而是**把失败的影响面切小**。

## Step 1: 单向审（只问一个问题）

派一个干净上下文的复核者，只回答这一个问题，**不得扩展**：

> 这份规划里，如果只有一处会导致整晚返工，最可能是哪一处？只给 1 个，给理由和触发条件。

要求输出结构固定：

```markdown
[最可能返工点] <一句话>
[触发条件] <什么输入/状态会让它发生>
[影响面] <会推翻哪些已完成部分>
[最小前置动作] <现在就做、能消除该风险的一步>
```

多给候选的一律打回重答——**排序而不是枚举**才产生信息。

## Step 2: 检查点划分

读取 `dispatch.md` 的并行组，确认：

- [ ] 每组完成后有独立提交（可单独回滚）。
- [ ] 每组完成后的检查命令明确（来自 `profile.commands`）。
- [ ] 组顺序上，契约定义方在消费方之前。
- [ ] 第一组足够小，能在你离开后 1 小时内完成——**先验证机制能跑通，再交给它跑长活**。

## Step 3: 中止条件

在 `preflight.md` 中写死"什么时候必须停下来"：

```markdown
# Preflight — <task>

## 单向审结论
<Step 1 的输出>

## 检查点
| 组 | 完成判据 | 提交信息 |

## 中止条件（满足任一立即停止，不得继续）
- 实际改动面超出 dispatch.md 声明的文件集合
- 某组检查失败且修复尝试超过 2 次
- 出现 dispatch.md 未列出的契约变更
- 需要修改 profile / workflow / spec 本身

## 恢复方式
<停止后如何从最近的检查点继续，或如何整体回滚>
```

## Step 4: 留一个醒来就能用的入口

在 `preflight.md` 末尾写明醒来后的第一件事：

```bash
git log --oneline <起始提交>..HEAD   # 看过夜产生的检查点
python .trellis/scripts/task.py current --source
```

## 什么时候不要挂机

任一条成立就该人工盯着：

- 任务本身还有未收敛的 P0（复核轮次到上限仍未过）。
- `dispatch.md` 里存在跨包契约变更且没有定义方优先的顺序。
- `profile.commands.test` 为空——没有自动验证的挂机等于盲跑。
